# Launcher working conventions

## Credential protection and public distribution

- Public source checkouts and new published builds must initialize with no projects, selected project, or developer-tool shortcuts. Never auto-import source/adjacent settings or embed personal settings. Preserve an existing Windows user's LocalAppData library. Explicit `--settings` remains a deliberate local override. The checked-in `launcher.settings.json` is an empty example only.
- All launcher API configuration saves use user-scoped DPAPI under `%LOCALAPPDATA%\FullStackLauncher\api-secrets\<UserSecretsId hash>\local.dat` or `prod.dat`. Encrypt temporary and backup files too. Keep protected empty stores authoritative and fail closed on invalid/unreadable ciphertext. Preserve snapshot conflicts, atomic saves, masked editing and value-free errors.
- **Import legacy values** explicitly stages only the selected profile's external .NET user-secrets for review/save. The user chose to preserve direct dotnet/EF compatibility: leave externally owned plaintext files unchanged and disclose that they remain plaintext. Never silently synchronize them or copy Local values into Prod.
- Managed API runs use a separate LocalAppData `api-runtime` artifacts folder with SDK-generated UserSecrets attributes disabled and UserSecretsId cleared only for that isolated build. Keep normal command-line build outputs and API source untouched. Require import/save when the selected legacy profile exists without a protected copy. Reject null/container overrides that cannot be represented in the child environment. Custom API configuration providers are outside the standard provider guarantee.
- Every WPF remote PostgreSQL connection uses VerifyFull with hostname/certificate validation and no GSS transport substitution. Preserve loopback development support, bound timeouts, and disable detailed error/security-info/parameter logging. Upgrade old saved Require/Prefer configurations in memory; never downgrade TLS to make a connection work. New saved connections persist normalized settings. Normalize recognizable PostgreSQL API connection overrides with the target driver's version in mind; reject unsafe ambiguous security settings with a value-free error.
- Reject recognizable literal credentials in start/clean/setup commands before saving and before starting/stopping for a restart. Redact known API values and common credential forms before all console display/copy, including JSON-escaped password fragments. Arbitrary application output, notes, and explicit database rows/schema exports are not guaranteed secret-free; do not present them as credential stores.
- `publish.ps1` never reads user settings and has no personal `-SettingsPath` option. Keep credentials, local settings/recovery files, notes, generated artifacts and old portable builds excluded from Git and MSBuild content. A new public EXE must contain no initial-settings resource. Old already-built EXEs are not retroactively sanitized.

## Archived projects and console apps

- `ProjectProfile.IsArchived` is a saved visibility preference, defaulting to false for existing profiles. The main sidebar uses `VisibleProjectItems` for Active/Archived filtering while `Projects`, `ProjectItems` and `_runners` retain the complete library. Archive/unarchive saves a detached settings candidate before changing runtime state. Preserve IDs, notes/drafts, queue data, database references, console buffers, passive refresh, production warnings and shutdown coverage. Archiving never stops commands. Return restored projects to Active and keep Archived reachable when no active projects remain.
- `ServiceProfile.Kind = "Console"` selects process-based status and permits omitted/empty URL and UI path fields. `IsConsole` is computed and not serialized. Saving console profiles clears web address fields and forbids API configuration; the full editor clears the API selection in the saved console candidate. Existing web profiles retain loopback URL validation and Local/Prod behavior. Preserve archive state and service options through every clone/edit.
- **+ Console project** opens a one-app profile; **Add console app** adds one to an existing project. Console cards show Run/Restart/Stop and captured output; web addresses, desired ports and API controls are hidden, and optional maintenance controls appear only when configured. Pass app arguments after `dotnet run --`, or use a quoted executable command with arguments. Keep commands user-configured; adding, selecting, archiving or editing a profile never starts it.
- Successful natural console completion uses `ServiceState.Completed`, permits another Run, and remains distinguishable from an intentional stop or failed command. Runtime results and logs remain in memory, outside settings. Keep port editing/proxy rewriting restricted to web profiles and ordinary batch actions scoped to the selected project's existing service instances.
- `ConsoleProcessSession` owns a Windows job for each console start/maintenance command. Create the shell suspended, inherit only its redirected standard handles, assign it to the job before resuming and retain the job for children that outlive their parent or run outside the working folder. Verify job membership on opened process handles plus PID/start-time identities; never infer ownership from executable names. Process-only inspection skips TCP/HTTP entirely. Stop/shutdown include owned jobs; unknown inspection remains an error. Drain trailing output before replacing/discarding a finished session. Completion reports the configured command's exit code, not independently observed child success. Commands receive EOF on stdin.

Drop confirmed-exited listeners from displayed conflicts, retain inaccessible/unknown blockers, and use the original TCP reports while waiting for actual port release. A stopped service with a real occupied port must say so; never conceal a current blocker or terminate replacement identities without another review.

## Development workflow

- Prioritize implementation during rapid development. Automated testing is deferred until the user explicitly requests testing or declares that a stable version has been achieved and asks for testing to begin. Do not decide on your own that the project is stable. This policy applies to the launcher, portable launcher, supporting scripts, existing test projects, and new tooling.
- Do not create, scaffold, build, run, or maintain automated test projects, console test harnesses, UI test scripts, test servers, fixtures, mocks, snapshots, coverage tooling, or test infrastructure during routine development. Do not add test frameworks or pipelines, or write, generate, update, or rewrite automated tests.
- Leave existing test assets in place. Report any incidentally encountered test failure without starting test maintenance. Disable test generation when using scaffolding tools; do not add test work merely to satisfy a generic convention or completion checklist.
- An explicit request for a specific test task authorizes only that scope and does not lift this policy for subsequent requests.
- Existing verification commands in launcher READMEs are retained for later use; they are not required checks during rapid development. Run them only when the user explicitly requests testing or declares a stable version and asks for testing to begin.
- Use focused application build or compiler checks when relevant, targeting the launcher application without building test projects. Documentation-only changes need no build or test run.
