## Service batch controls

**Start all** starts only stopped services that can start. It stays disabled while status is checking or no service can start. When every configured service is running, the button turns gray and a green **Running** indicator appears beside it. The disabled button still explains its state on hover. Status comes from the existing process and endpoint checks, including services started externally, and refreshes every three seconds.

**Restart all** and **Force stop all** remain explicit actions. Agent completion no longer triggers service restarts; the former automatic-restart and watch-folder preferences remain inert for settings compatibility.

## Long Running Task

The **Long Running Task** switch in **Sections ▾** keeps the computer and display awake while the dashboard is open, including when minimized. It also sends a tiny pointer nudge and return after about one minute without keyboard or mouse input. Nudges wait while keys or buttons are held and pause when the dashboard's input desktop is unavailable, including the lock screen. No clicks or keystrokes are sent, and no windows are focused.

The choice is saved with your launcher preferences and defaults to off. Uncheck it or close the dashboard to stop; leaving the separate Codex watcher running does not retain this mode. Canceling dashboard closure keeps it active. If saving fails, the current session still uses your choice and the dashboard reports that it could not be remembered. Explicit sleep and Windows policies still apply. This manual mode is separate from automatic queue execution and its temporary keep-awake request.

Teams determines its own presence, so this feature cannot guarantee an **Active/Available** status. See [Microsoft's Teams status guidance](https://support.microsoft.com/en-us/teams/notifications-settings/change-your-status-in-microsoft-teams). Sleep prevention uses the Windows [SetThreadExecutionState API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate).

The workspace shows changed files and tracked-text lines **added / removed** against the same-named branch on the selected remote. Totals include local commits and current tracked-file edits; untracked files contribute to the file count and are excluded from line totals. Uncommitted files and commits ahead/behind are shown underneath. Comparisons use **last fetched** history. If that cached remote branch is missing, including a new or remotely deleted feature branch, both the workspace and dashboard still show staged and unstaged tracked-file changes against the last local commit (`HEAD`). This fallback is labeled **Local changes · since last local commit**, and unavailable remote ahead/behind counts are omitted. It does not compare with another remote branch or change Git state. Binary and untracked contents remain excluded. A failed read offers Retry. There is no file-by-file viewer.

- The header defaults to the current branch. Click its pencil to edit a branch name in the single central branch editor. **Switch branch** checks out an existing local branch or creates a tracking branch from a last-fetched remote branch; **Create branch** creates and checks out a new branch. Windows animation preferences are respected, and the text remains available without motion.

**Merge Locally** is a separate local merge action. Every use first opens **Verify remote source branch** immediately, showing the current local branch. The chooser shows its own loading spinner while checking local status and reading branches from the active remote; the main workspace stays in place. Search and confirmation become available after the list loads. Empty results and selectable failure details stay in the chooser, with **Retry** for a failed read. Cancel, Escape, or closing the chooser cancels the read and waits for it to finish. **Confirm branch & compare** immediately checks the latest source for commits missing from the current branch and shows the Git conflict comparison. If the current branch already includes every source commit, the result says it is up to date; **Back to Git** returns to the commit controls without a checkpoint, merge, or recovery record. If incoming commits exist, the result shows their count and any conflicts before **Review local merge…** opens the approval step. Known conflicts require manual resolution if you approve the merge. **Config → Change release branch…** also changes the saved source. The choice is stored in local Git configuration and bound to the remote URL; confirming the unchanged source does not rewrite it. Both source and destination must use the same fetch/push repository for this workflow.

A saved release source always takes priority. With no saved source, the first Git load suggests a branch from locally cached refs for the active remote: a unique exact `release`, one `release/*` or `releases/*`, the cached remote HEAD, then a unique `main`, `master`, or `trunk`, in that order. Ambiguous matches leave the source unselected. If no saved source or suggestion exists once the Git workspace is ready, the launcher opens **No release branch detected** and asks you to choose a source. Cancel keeps Git usable and prevents repeated prompts for that repository and remote connection during the same window session; choose **Config → Change release branch…** later. Setup and other dialogs finish before this prompt opens. Config identifies the suggestion as cached, and the chooser preselects it. The chooser verifies the suggestion against its fresh full remote branch list; only explicit confirmation saves the choice. Merge and conflict-check confirmations remain required. Detection itself makes no network request and never saves configuration or changes the checkout.

**Git-only conflict test**, beside the merge button, opens the same branch verification and runs the comparison immediately after confirmation, without waiting for agents or queues. Its result opens in the Git workspace, with incoming commits, conflict paths, exact compared commits, and Git diagnostics. The result is also retained in the **Git Commit** comparison when no separate dashboard check is pending. The comparison uses the current committed branch and the latest selected remote source with `git merge-tree --write-tree`; source or local branch changes during the check discard the result and require another comparison. The check does not start a merge, stage, commit, push or change local files, HEAD, the index or cached remote refs. It downloads missing Git objects and may write temporary merge-result objects. No application build or tests run. Uncommitted edits, untracked files and changes inside submodules are excluded; the result identifies the exact commits checked and does not guarantee that an actual merge including those edits will be conflict-free. Git 2.38 or newer with modern `merge-tree` support is required for conflict simulation; **Merge Locally** skips that simulation when the current branch already includes the exact source commit. Unsupported simulation, unavailable history and command failures are reported as unavailable checks, never clean results. Checks requested from the dashboard remain manual queued checks. Background checks suppress credential prompts and require recognized credential helpers and existing verified SSH trust.

The check refuses configured external merge drivers and renormalizing external filters because those commands could change files. No actual merge or automatic conflict resolution is used as a fallback.

The preparation review identifies the current branch and explains the local checkpoint; it does not ask for a new branch name. After approval, the launcher rechecks the reviewed branch, local state, remote configuration, and exact source commit, then fetches the tracked source. A changed source or failed fetch stops before creating a checkpoint or recovery record. If incoming commits remain, the launcher preserves dirty local files in an automatically named local checkpoint commit on the current branch, then merges the exact fetched source commit with no automatic stash or merge commit. Status text reports source verification, fetching, incoming history, checkpointing, integration, and the result. This preparation requires an existing local commit and shared source history. It never creates a branch, pushes, or opens a commit-and-push review automatically.

If Git reports conflicts, a dedicated window lists the affected paths. Resolve and stage them in your editor or Git, then refresh. A conflict-free result stays local. When ready, choose **Commit all & push…** to review the destination branch and an editable prepared commit message; this same action finishes a tracked merge or publishes ordinary local changes. Closing its review leaves the work local. If you choose a new destination while a merge is pending, the launcher commits that merge on the current local branch first, then creates the new branch from the result and pushes it. Other existing local or remote branches require a separate switch and review; they are not silently reused as new destinations.

Merge recovery stores only operation identities, branches, commit IDs and a remote fingerprint in the checkout's Git metadata. Cancellation, changed identities and uncertain push outcomes retain that record and the local work for review; nothing automatically retries or rolls back. A confirmed local commit is reused on an explicit push retry. **Clear merge tracking…** only dismisses the launcher's record after you review the Git state; it does not undo a merge, delete checkpoints or prove that a push completed. Standalone **Push** remains available for existing-commit retries outside a tracked merge; a pending tracked merge must go through **Commit all & push…**. If the branch-creation reflog has expired or is unavailable, the dialog says creation history is unavailable rather than guessing from commit dates.

**Refresh local status** rereads local data. Use **Fetch** to update remote comparisons. Review canceled or interrupted operations before retrying; their outcome can be uncertain.

Dashboard startup checks saved Git connections in configured project and service folders quietly in the background. Choosing **Open Git…** in **Git Commit** loads local information; explicit connection checks can share an unfinished check or reuse authentication verified earlier in this launcher session. Older verification is labeled with its session context. Git still checks access for each network operation. These checks do not fetch branches, stage, commit or push.

Nonempty folders are never overwritten; choose New repository for existing local files, or select an empty configured folder through Config. ## Run from source

The launcher source lives at the root of the standalone `FullStackDeveloperTool` repository. Run the commands below from the folder containing `FullStackLauncher.csproj`.

Double-click **launch.cmd**. It builds the launcher in Release mode and opens its window. Building requires Windows and the .NET 10 SDK or a newer compatible SDK.

You can also run:

```powershell
dotnet run --project .\FullStackLauncher.csproj
```

The launcher needs the same tools your projects normally use on `PATH`. For example, an ASP.NET Core and Angular project needs its backend's .NET SDK, plus a Node.js/npm version supported by its Angular frontend. The default single-file build includes the launcher's .NET runtime; it does not install SDKs, Node, npm, or databases for your projects.

## Start with your own projects

A new Windows user starts with no projects, selected project, or developer-tool shortcuts. Source checkouts and published EXEs do not import the author's settings or carry personal project profiles. Choose **+ New project**, then **Use local folder** or **Integrate from DevOps or Git**. Local setup asks for the project root in the compact folder step. Continue to automatically select **Angular Full Stack**, **Console project**, or **Flutter / Dart app** from recognized project files. You can change the type before reviewing commands. Unrecognized or mixed project folders require a manual type choice. Returning to the same root preserves that choice; changing the root detects again. All types use the same setup and command review flow. The root `launcher.settings.json` is an empty example, not an automatically imported settings file.

Remote import currently supports Azure DevOps Services; other Git providers are coming next. Enter `https://dev.azure.com/organization/project`, a corresponding `organization.visualstudio.com` project URL, or a complete Azure repository URL. ## API secrets and Local / Prod configuration

Each .NET API service card has **Functions** and an **API settings** cog; Statistics is inside Functions. **Change DB** appears only on its Database cards, titled with the database name followed by **Database**. The cog opens **Launch profile…**, **Manage secrets & settings…**, and **Use Local & restart**; the quick **Use Prod & restart** action is removed. Choose the store to edit, select or add a key such as `DefaultConnectionString` or `ConnectionStrings:DefaultConnectionString`, enter its value, choose **Stage value**, then **Save changes**. Removing an override is also staged until saved. The key list includes appsettings key names and source filenames; stored values stay masked until you explicitly reveal the selected value. Failed saves retain drafts, and concurrent edits require a reload before saving.

Local and Prod save separate Windows-user encrypted files under `%LOCALAPPDATA%\FullStackLauncher\api-secrets\<project-secret-ID hash>\`. Windows DPAPI protects their contents, temporary files, and backups; no new plaintext credential files are written. Values stay out of project profiles, public builds, and command arguments. This manages configuration for the locally running API, not Azure deployment settings. Changing the editor's profile does not activate it.

When no `UserSecretsId` is declared, stores instead live under `api-secrets\by-project\<absolute-project-path hash>\`. Local and Prod remain separate. Moving that API project or adding/removing its declared ID requires a fresh configuration review; the launcher does not silently migrate secret stores.

To reuse existing configuration, choose **Import legacy values**, review the staged values, and save. Import is specific to the selected Local or Prod profile and never copies Local into Prod. The original `.NET UserSecrets` files remain unchanged for direct `dotnet`/EF workflows. Those externally owned files are still plaintext; the launcher neither silently synchronizes them nor rewrites them. An encrypted profile remains authoritative even when all its overrides have been removed. A managed launch with legacy secrets but no encrypted profile asks you to import/save first.

**Use Local & restart** preflights Local configuration and saves its selection, then starts or restarts that API. **Launch profile…** shows the command and lets you edit supported launch options for the next explicit Start or Restart. This editor always uses Local and has no profile selector. Save never starts or stops the API. API cards omit the duplicate inline command shown in this modal; frontend cards also hide commands; console and command-based API cards retain their commands. Existing production configuration stores remain separate: Prod must contain saved values, including an explicit nonempty production value for every connection-string key declared in base, Development or Production appsettings or discovered in the readable Local store; Local values are never copied to Prod automatically. An invalid inactive store does not block switching to a valid store. A failed selection save leaves the current API running. Failed stops/starts retain the selected profile and report the running environment separately rather than claiming it applied.

After opting into these controls, API starts use `dotnet run --project <project> --no-launch-profile` with the configured local listening address. The launch editor saves supported build options separately from the legacy start command; Clean and Setup retain their saved commands. Managed builds always use an isolated artifacts directory under LocalAppData and disable the SDK-generated UserSecrets attribute. Named source launch profiles, custom project/output paths and app arguments cannot override these managed settings. This keeps the standard Development provider from reviving old plaintext overrides without changing ordinary command-line build outputs. It requires a .NET 8 or newer compatible SDK; APIs with custom configuration providers remain responsible for their own provider order.

Local sets both .NET host environments to `Development`; Prod sets them to `Production`. Selected secrets are passed through the child process environment, above `appsettings.json` and the environment-specific appsettings file. Inherited hierarchical configuration, connection-string aliases and host environment/URL settings are removed. Ordinary process variables remain. Runtime/OS control keys cannot be used as application secrets. Environment variables and decrypted values exist in process memory; DPAPI does not protect against software already running as the same Windows user.

Configuration changes apply on restart. Managed launches cannot represent JSON null/container overrides through environment variables: replace them with text values or remove the overrides before launching. A separately launched Development API continues using its own normal user-secrets provider. Environment selection alone cannot establish which database a value points to; configure both encrypted profiles deliberately.

Prod selection or an applied Prod process shows a red service section and a persistent production banner, including when services are hidden or another project is selected. The API settings popup shows **ACTIVE** only after a launcher-managed API responds locally; external processes are labeled **ENVIRONMENT UNVERIFIED** there until restarted through a configuration button. API headers omit service-type and environment badges. Production uses the API's real Production behavior: this CRM disables Swagger, Development diagnostics and Power Settings, and enables its secure-cookie/HTTPS rules. Set up local HTTPS when required; an existing `/swagger` UI path will return 404 in Production.

The Release launcher application build passed with zero warnings/errors, and `publish.ps1` produced the updated self-contained `publish/single-file/FullStackLauncher.exe`. Automated tests remain deferred under `AGENTS.md`; live secret editing and API switching were not exercised against real credentials or production data.

### Chat progress overlay

The alerts window's **Chat progress** tab shows the same list; **All tasks and agents** provides project labels and individual agent estimates beside their statuses.

Percentages marked **~N% est.** are low-confidence elapsed-time guesses, not measured work completion or a guaranteed finish time. Database information appears in separate cards titled with names discovered from the service's Local API configuration, without a duplicate DB tag on API service headers. Cards omit routine source text and keep actual discovery, restart, or change errors visible; no database health endpoint, direct database connection, or comparison is used. Every service captures output independently of its card or console window. Use **Functions → Console** on API and frontend cards or **Console ▾** on other cards for **Copy output**, **Clear output**, **Expand output ↗**, and **Copy Errors** when errors are retained. Copy and Clear are disabled when the retained buffer is empty. Service actions and new output never open the console automatically. If retained output contains an error, that service shows a separate **ERROR IN OUTPUT** indicator while its process status, including **RUNNING**, remains visible. **Copy Errors** copies all retained errors with up to 10 preceding console entries per error, in capture order, without opening the console. Overlapping context is copied once. A brief **Copied Error** popup confirms a successful copy. Clear its output to dismiss the indicator; warnings and stderr alone do not set it. **Expand output ↗** opens a resizable live window for that service, with severity filters and oldest-first, newest-first, or errors-first sorting. The console windows use a dark background with mint accents, cyan commands, light ordinary output, mint success, amber warnings, coral errors, and lavender information. Timestamps and explicit labels distinguish the categories without relying on color. Each service retains 600 entries used by its output actions and console window. Copy all includes every retained line even when filtered; Clear clears the service buffer and rejects older queued output while new capture continues. Output stays in memory and is not saved with settings. Existing API secret redaction applies before display.

Restarting or stopping an API/frontend clears its previous console output after validation and any required conflict confirmation. New lifecycle messages, startup output, and failures remain visible; queued output from the previous run cannot reappear. Console apps retain their command history until explicitly cleared. Hiding Services or closing a console popout leaves capture active. Output comes from commands started by this launcher; it cannot attach to an external process's existing terminal output. When you exit with apps left running, a background helper keeps their output pipes readable and discards the output without saving it. Retained console history is lost when the launcher closes, and reopening does not reattach output capture to those preserved runs. Restart an app through the launcher to capture its new output.

Database **Connected** status comes from Local configuration discovery and does not depend on an API database health response. Existing Codex diagnostic workspaces retain their own operation histories.

The dashboard refreshes process and local listening-port status automatically and captures command output. Web launch buttons sit beside the service status and running port with an 8-pixel gap. In narrow layouts, the status and launch button stay together on a second row beneath the name and menus. Healthy API, frontend, and Database cards share a 32-pixel header row and a 70-pixel card height; real errors, details, and wrapped content can increase the height. Ready launch buttons share a green outline and a soft 2.4-second glow pulse. The pulse stops when a button is unavailable, disabled, or hidden, and Windows reduced-motion settings leave a static highlight. A started process is not necessarily ready to serve requests: the launch button stays gray while the service is stopped, starting, busy, or checking readiness. Swagger launch buttons turn yellow when the API is responding but Swagger UI is not detected or cannot be reached; their hover message distinguishes a missing or disabled UI from authentication, server, transport, or certificate errors. Only a successful check of the configured local Swagger UI turns its button green. Checks run in the background and refresh periodically, without changing API configuration or starting services. Clicking an unavailable launch button explains the reason; it does not open a browser. The label follows the destination: **Launch Swagger** for `/swagger`, **Launch Landing Page** for a frontend root, and the page name for a custom path. Service cards omit address rows and the ordinary stopped-process message; errors, conflicts, and startup details remain visible.
Only `http://` and `https://` loopback URLs are accepted in project settings. A listener already using an expected port is reported separately from a process started by this launcher. The launcher does not claim ownership of every `dotnet` or `node` process on the machine.

**Force stop** terminates the service's process trees. **Restart** performs that stop followed by the start command. These explicit actions can also stop an externally started service when its executable or command line can be tied to the configured working folder. When a verified external process owns exactly one listening port, the launcher can use that port for its URL.

When a service shows **Conflict**, its card offers **Resolve conflict & restart**. The confirmation lists the names and PIDs of the blocking processes and their current children. Confirming force stops those processes plus this service's matching processes, waits for the port to clear, and runs this service's start command. Unsaved work in the listed processes may be lost. Recovery checks process start times to avoid stopping a reused PID, protects the launcher and its ancestors, and requires another review if a replacement process takes the port. It never stops all Node or .NET processes by name. If Windows denies access or a supervisor respawns the listener, the service shows an error/conflict so you can stop it in its original application and retry. Ordinary Restart all and launcher shutdown do not clear unverified conflicts.

**Force stop all** also includes services whose ports are blocked even when the service itself is stopped. It stops normal service trees first, then reviews conflicting processes one service at a time with the same identity safeguards, leaving approved services stopped. Canceling a conflict review preserves that blocker and reports that attention is still needed. New service commands are disabled during the batch. A stopped service with a genuinely occupied port explicitly says the service is stopped and identifies the blocking PID; an exited listener or a released old detected port does not remain a conflict.

Opening another dashboard EXE automatically replaces the dashboard using the same settings file in the same Windows user/session. The old dashboard keeps its apps running, saves verified process/job identities, and exits before the new dashboard loads them. No service stop/restart command runs during this handoff. The watcher and queue owner remain independent. Unsaved drafts still require resolution; finish open dialogs and service operations before switching versions. Concurrent launches are serialized. Different explicit `--settings` libraries can remain open separately. Versions published before this handoff feature must be closed once with **Leave running & exit**. Normal keep-running recovery limits below still apply, including loss of console capture and unverified API configuration after reopening.

Closing the launcher with active apps opens a dark, mint-accented **Leave apps running?** window listing their project and service names. **Leave running & exit** keeps those apps active after the dashboard closes. **Force stop & exit** immediately stops the verified service process trees before closing; in-progress requests or work may be interrupted. A failed stop or handoff keeps the launcher open with an error. **Cancel**, Escape, or the window's close button keeps the launcher open without stopping apps. Cancel receives initial keyboard focus, and force stop is never the default action. Draft resolution and the separate Codex watcher choice still apply.

For later discovery, the launcher stores service IDs, configured folders, process IDs and start times, and console job identities under `%LOCALAPPDATA%\FullStackLauncher\service-runtime`. It rechecks live process identities and configured-folder evidence rather than treating a saved PID or occupied port as ownership. Unrelated listeners remain conflicts and are not automatically terminated. Reopening does not recover the applied API environment or credentials: rediscovered APIs remain unverified until the launcher explicitly starts them with a validated configuration.

## Saved projects and local storage

`%LOCALAPPDATA%\FullStackLauncher\launcher.settings.json` holds all project/service profiles, the selected project, developer-tool shortcuts, inert legacy database references, and workspace section visibility/split proportions. Source builds and published copies share this store by default. Add, edit, or remove projects in the dashboard; an intentionally empty list stays empty. Existing settings without layout preferences use the default layout.

When the local settings file does not exist, the launcher creates an empty project and shortcut library. It does not import source-folder, adjacent, or embedded profiles. Existing local settings remain in use, so updating the app on your own account preserves your setup; a new user's account gets a blank slate. Old portable files remain untouched and can be used only through an explicit `--settings` choice.

Project root paths are relative to the **settings file's folder** unless absolute. Service working folders are relative to their **project root** unless absolute. The folder browsers save relative paths whenever the folders are on the same drive. Moving only the EXE does not affect these paths. If you move a repository, update its project root in the editor. Existing folders are required when saving a project.

Choose another settings file explicitly when needed:

```powershell
.\FullStackLauncher.exe --settings "D:\My projects\launcher.settings.json"
```

An explicit `--settings` path uses only that file. A missing explicit file starts empty, and saving creates it. Saves replace the file atomically and retain its previous version as `launcher.settings.json.bak`. Malformed settings are preserved, with an additional timestamped recovery copy when possible; the app displays a warning and disables saving instead of overwriting them. Fix the file and restart, or launch with another `--settings` file. If another launcher copy or program changes valid settings while the launcher is open, restart to reload them before saving.

Project profiles and notes are ordinary local data, not credential stores. Commands containing recognizable literal passwords, tokens, or credential URLs are rejected before saving/starting; use encrypted API configuration or the launched application's credential provider. Console output is filtered for known API values and common credential formats before display/copy, but arbitrary applications must still avoid printing secrets. The launcher does not read database rows or export schemas.

## Build a single-file EXE

From this folder, run:

```powershell
.\publish.ps1
```

The script publishes exactly one file, `publish\single-file\FullStackLauncher.exe`, as a self-contained Windows x64 app. For Windows ARM64, use `./publish.ps1 -Runtime win-arm64`. Publishing may download runtime packs from NuGet. For a smaller EXE that requires the .NET 10 Windows Desktop Runtime on the destination, use `./publish.ps1 -FrameworkDependent`. Native runtime libraries are bundled and extracted by .NET when the EXE runs; no companion distribution files are required.

Publishing never reads or embeds source settings, local saved settings, credentials, notes, or project profiles. The old `-SettingsPath` publishing option and embedded seed hook have been removed. Every newly published build initializes an empty library for a new Windows user. Publishing does not change your existing local library.

Copy just **FullStackLauncher.exe** to your desktop or another location and open it. The dashboard and Codex watcher both run from this file and keep their local settings through subsequent EXE replacements. On another Windows account or machine, add your own projects and provide their development tools and credentials. Older EXEs already produced with personal embedded profiles are not retroactively sanitized; distribute a newly published build.

Republishing can replace an EXE in the same single-file output folder. Alternative output folders must remain inside this source folder. The script rejects folders containing other files, preserving older `portable` folders and their saved profiles. Use a new empty output folder when needed, then copy the resulting EXE elsewhere.
