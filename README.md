# Full Stack Launcher

**Functions ▾ → Hard Reset Codex** prepares a restart, then asks for confirmation before force-closing Codex and ChatGPT processes in your Windows session. Unsaved work, running chats, and CLI sessions may be interrupted. Each affected desktop app reopens once; its background processes are recreated by the app. CLI sessions are not replayed. If Codex has already crashed, the installed desktop app can still be opened. Restart progress and any failures appear in the launcher.

Agents connected through the [local bridge](docs/agent-bridge.md#agent-change-summaries) can discover a project's active Git connection and submit short completed-change bullets. **Commit all & push** combines those reports into an editable commit message. Reports remain pending until a reviewed local commit succeeds; submitting a report never stages, commits, or pushes files.

Open **Sections ▾** and turn on **Next commit** to open a resizable panel along the full window height on the right. Functions, Alerts, Edit, and Refresh sit at the top right of the workspace header. The panel follows the selected project and checks for new AI updates every three seconds. Its cog opens repository selection, preview details, the full character count, and the optional PR sound reminder. The reminder starts off each session and sounds after five minutes, then every five minutes while the panel is visible and the message exceeds 3,000 characters. The panel shows one complete next message, Copy message, and characters remaining directly below **Commit message**, replaced by an explicit warning above 4,000 characters. Commit review and the commit service enforce the same limit without truncating text. Click outside the settings popup or press Escape to close it.

Unread AI text appears mint and underlined inside the message. Click the message, or press Enter while it has focus, to acknowledge the displayed updates. After a successful save, their text returns to the normal readable color and the underlines disappear. Later arrivals and updates excluded from the message remain unread. Scroll, focus, selection, and copying do not acknowledge updates on their own. Read status is saved in that checkout's Git metadata and never removes an update from commit review. Custom Git messages remain intact for this app session. An open commit review keeps its exact message and flags later AI arrivals for another review. Panel visibility is a saved layout preference; message drafts never enter launcher settings.

Above the commit message, **Git comparison** shows the Git workspace's changed-file count and tracked lines added/removed against the selected remote's same-named cached branch, labeled **last fetched**. Local totals refresh every 30 seconds; untracked and binary contents remain excluded from line totals. The cog in the card's top-right corner contains **Git-only conflict test** and **Details…**. The test queues a manual check against the release branch saved in Git. Details opens the exact compared commits, conflict paths, and Git diagnostics after a confirmed result. Conflict status appears only after a manual request; its tooltip shows the source, checked time when available, and excluded uncommitted edits. Zero ahead/behind counts are omitted.

Conflict checks run only after a manual request from the comparison cog or Git workspace; there are no periodic or startup conflict checks. Requests do not read agent activity, wait for idle chats or queues, or pause for launcher service reservations. Duplicate requests become one pending check, and conflict tests run one at a time. Repository, branch, active connection, reviewed snapshot, and process-exit checks remain enforced; concurrent Git changes invalidate the result rather than reporting a stale success. Unconfirmed Git process termination pauses further checks until that exact process is confirmed stopped. Closing cancels and drains pending Git work; canceled closure resumes the manual queue. Requests and results remain session-only.

A Windows WPF dashboard for your development services and console apps, distributable as one executable. Save and archive projects, see process status and console output, run commands with arguments, and stop tracked processes. Web services also have local endpoint checks and browser shortcuts. Your projects and preferences are kept in your Windows user account's local application data, so moving or replacing the EXE keeps them available.

The dark theme uses explicit light text on service cards, database health cards, and copy menus, with readable muted labels for disabled buttons. The mint terminal/stack icon is embedded in the executable and all launcher windows for the title bar, taskbar, and File Explorer. Icon source artwork, sizes, and regeneration instructions are in `Assets/README.md`.

The Projects sidebar shows each configured app or service by name with a live status label and colored dot. Green means running or a successfully completed console command; amber means starting, working, or stopping; red means a conflict or error; gray means stopped or awaiting the first check. At startup, the launcher checks every saved project's processes and local ports before enabling service commands. Apps left running from a previous launcher session appear with their current status; their Start controls remain disabled to prevent duplicate starts. Every saved project is then checked on the existing three-second refresh timer, including projects you have not selected or have archived and while sections are hidden. These indicators share the service cards' process checks and web services' local HTTP checks, including services started externally. Hover over a status row for its latest detail.

Each frontend/backend service card has a **Statistics** shortcut. Its compact popup aligns **Lines** with **Count** or **Recount** and shows **Avg / file** beneath it. Counts run in the background with a progress bar; the new values appear after completion. Average file size is total physical lines divided by the counted file total, including empty source files, rounded to one decimal place. No counted files shows **—**. Recounts show the signed difference from the previous successful count using the same exclusions, including **0** when unchanged. The first count establishes a baseline. Hover over the line total for file count, timestamp, previous value, and counting scope.

API statistics also show **Endpoints** with an aligned **Count** or **Recount** button. Opening API statistics performs the first source count automatically. An indeterminate progress bar stays visible during the scan; the result appears after it completes. The API folder must have a named Git branch selected. The existing branch is used without another confirmation; detached checkouts or folders without a selected branch offer **Select branch…** for that API folder. Counting never checks out a branch, starts a service, or fetches a remote. Counts describe distinct HTTP verb and route pairs discovered in source, including uncommitted code. A **partial** marker and tooltip preserve discovery limits; **Details…** opens the existing route inventory and local OpenAPI import.

Counts include all physical lines, including blank lines and comments, in recognized source, markup, style, script, and configuration files, including untracked files. Dependency, build, output, cache, and version-control folders, binary files, links, **package.json**, **package-lock.json** and other lockfiles, and recognized minified/generated artifacts are excluded. Angular application configuration such as **angular.json** remains counted. Source scans run only when requested and never start or stop services. Failed or incomplete scans keep the last saved count and average. History stays in the Windows user's local `FullStackLauncher/source-line-counts` folder, isolated by settings file, project, service, and resolved service folder; moving a service to a different folder starts a new baseline. Counts saved before the package manifest exclusion stay visible as **recount needed**; the next successful recount applies the new exclusions and establishes a fresh baseline instead of reporting the exclusion change as a code change. The average appears after this recount. History upgrades only when a new count is saved; older launcher builds cannot read the upgraded history.

Each project also shows its current **Git branch** in the sidebar. Branch information refreshes every three seconds, when the dashboard regains focus, and with **Refresh**. The launcher checks the project root and each configured service folder, using their nearest Git repository; shared repositories appear once, while separate repositories get labeled rows. Hover for full branch names and folder details. Detached checkouts show a short commit ID; folders outside Git, missing folders and unreadable metadata have explicit status labels. Branches are read directly from local Git metadata, including linked worktrees and submodules, without requiring Git on PATH. This is the folder's current checkout, not necessarily the branch used to build an already-running service. Branch information stays in memory and never changes a checkout or saved settings.

Frontend service cards have an **Open after build** checkbox in **Console ▾**, off by default and saved per service. It applies to the next launcher-managed start or restart, including batch and agent restarts. The launcher waits for a recognized successful build/readiness message, an owned local listener, and an HTTP 200–399 response. Selecting a project, enabling the checkbox for an already-running service, passive detection of an external process, failed builds, and ordinary hot reloads do not open the browser. Angular, React, Vue, Vite, Next/Next.js, and Frontend service kinds are supported; custom output without a recognized success message remains unopened.

Before opening, the launcher checks for an existing tab at the same local site. Different application routes and localhost/127.0.0.1/[::1] aliases at the same scheme and port count as the same site. Existing tabs stay untouched. When no browser window is open, it opens the default browser. Active Chrome/Edge addresses can establish that the site is already open; reliable background-tab checks use the paired Browser Capture extension in every open Chrome/Edge profile. Reload the updated extension after upgrading. Unpaired profiles, unavailable tab access, unsupported open browsers, and incomplete window inventories skip automatic opening and report the reason in the status area and checkbox tooltip. Disabling the checkbox, stopping the service, replacing its profile, or closing the launcher cancels pending checks. No page content is captured for this feature.

## Service batch controls

**Start all** starts only stopped services that can start. It stays disabled while status is checking or no service can start. When every configured service is running, the button turns gray and a green **Running** indicator appears beside it. The disabled button still explains its state on hover. Status comes from the existing process and endpoint checks, including services started externally, and refreshes every three seconds.

**Restart all** and **Force stop all** remain explicit actions. Agent completion no longer triggers service restarts; the former automatic-restart and watch-folder preferences remain inert for settings compatibility.

## Long Running Task

The **Long Running Task** switch in **Sections ▾** keeps the computer and display awake while the dashboard is open, including when minimized. It also sends a tiny pointer nudge and return after about one minute without keyboard or mouse input. Nudges wait while keys or buttons are held and pause when the dashboard's input desktop is unavailable, including the lock screen. No clicks or keystrokes are sent, and no windows are focused.

The choice is saved with your launcher preferences and defaults to off. Uncheck it or close the dashboard to stop; leaving the separate Codex watcher running does not retain this mode. Canceling dashboard closure keeps it active. If saving fails, the current session still uses your choice and the dashboard reports that it could not be remembered. Explicit sleep and Windows policies still apply. This manual mode is separate from automatic queue execution and its temporary keep-awake request.

Teams determines its own presence, so this feature cannot guarantee an **Active/Available** status. See [Microsoft's Teams status guidance](https://support.microsoft.com/en-us/teams/notifications-settings/change-your-status-in-microsoft-teams). Sleep prevention uses the Windows [SetThreadExecutionState API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate).

## Git workspace

Choose **Git…** beside the selected project's controls. Use **Config** to pick the project or service folder and active remote, and inspect the repository path. Actions use that folder's nearest repository, which can be a containing folder. Separate service repositories remain independently selectable. The main header shows one green branch name with a pencil; repository and remote details stay in Config. The workspace requires Git for Windows on `PATH`; the existing passive sidebar branch display still reads local metadata without Git or network access.

Opening the workspace shows a simple spinner while local status, an automatic fetch of the active remote, the initial diff and connection routing load. Selecting another folder or active connection also fetches during loading. Remote branches and comparisons use the refreshed refs before content appears. Automatic fetch is noninteractive; if it fails, local status and cached remote history remain available with error details and the manual **Fetch** action. Folder paths, remote selectors and setup instructions stay hidden during loading. A failed status/diff/workflow read shows one central **Retry** that reruns loading and fetching only. Confirmed action results remain available when a later reload fails. If Git process termination is unconfirmed, Retry first checks that the captured process has exited before reading again; other actions and closure remain blocked.

The workspace shows changed files and tracked-text lines **added / removed** against the same-named branch on the selected remote. Totals include local commits and current tracked-file edits; untracked files contribute to the file count and are excluded from line totals. Uncommitted files and commits ahead/behind are shown underneath. Comparisons use **last fetched** history. If that cached remote branch is missing, including a new or remotely deleted feature branch, both the workspace and dashboard still show staged and unstaged tracked-file changes against the last local commit (`HEAD`). This fallback is labeled **Local changes · since last local commit**, and unavailable remote ahead/behind counts are omitted. It does not compare with another remote branch or change Git state. Binary and untracked contents remain excluded. A failed read offers Retry. There is no file-by-file viewer.

- The header defaults to the current branch. Click its pencil to edit a branch name in the single central branch editor. **Switch branch** checks out an existing local branch or creates a tracking branch from a last-fetched remote branch; **Create branch** creates and checks out a new branch. Both require a clean working tree and no pending operation. Enter or the check icon keeps only the destination draft for the next **Commit all & push…**; Escape cancels the edit. A planned new destination is labeled **Publish branch**, with the actual current local branch in its tooltip and action review. Typing changes only a session draft; it does not rename, create or switch a Git branch. Drafts stay scoped to the repository, current branch and active remote. Release merges and Git-only conflict tests always use the actual current local branch. The redundant generic merge dropdown is removed; routine action explanations are available in tooltips.
- **Commit all & push…** reviews the destination entered in the header, the current branch and the most recently created local branch found in retained Git reflogs. The destination is fixed during review; cancel to change it in the header. The commit message is prepared automatically and remains editable. Confirming stages all additions, edits and deletions from the displayed repository root, commits them, and pushes the chosen same-named branch on the selected remote with upstream tracking. A new destination carries the current local history and files; the flow never resets another existing branch. Ignored untracked files stay ignored, and changes inside a submodule require a separate commit in that submodule. If there are no changes, the action pushes existing commits. A confirmed local commit remains saved if pushing fails; use **Push** for those existing commits after reviewing the outcome.
- **Push** shares existing local commits to the selected remote without staging or creating a commit.
- **Fetch** refreshes the selected remote's cached branches and removes stale tracking references.
- **Pull** brings in the selected remote's same-named branch with a clean working tree and fast-forward only. It never rebases or stashes edits.

The **Branches** tab opens directly using refs fetched during workspace loading; revisiting it never prompts or fetches again. The list defaults to **Remote branches** from that active remote only. The dropdown at the top right switches to **Local branches**. Remote rows show their own history without comparing them to your current local branch; **Commit history…** shows only commits reachable from the selected remote tip, 30 per page. Local rows retain ahead/behind counts and history from both local branches, labeling shared and branch-only commits. Counts exclude uncommitted edits. Previous/Next keep the same captured tips; changed refs require refreshing and selecting again. Shallow or partial clones report unavailable history rather than incomplete counts. Row selection never switches branches or fetches. Exact redacted errors remain selectable in **Error details** for the latest operation.

After you confirm **Commit all & push…**, an inline animated indicator follows the actual operation phases. A confirmed push shows a success check and brief burst; failures and cancellation show **Push not confirmed** with details. Windows animation preferences are respected, and the text remains available without motion.

After a confirmed successful **Push** or **Commit all & push…**, the launcher displays a clickable after-push link with **Open Azure** and **Copy link** buttons and opens it in Google Chrome. Azure DevOps connections default to their repository page. Use **Config → select a connection → After-push link…** to save another HTTP or HTTPS link, restore the repository page, or leave it blank to disable opening. The button reads **Open link** for a customized destination outside Azure. Each setting stays in local Git configuration, bound to that connection's push destination. Chrome reuses an existing window; if none is open, the launcher requests a new window. Browser errors leave the successful push intact and keep the open button available for retry. Failed or unconfirmed pushes never open the link.

**Merge Locally** is a separate local merge action. Every use first opens **Verify remote source branch** immediately, showing the current local branch. The chooser shows its own loading spinner while checking local status and reading branches from the active remote; the main workspace stays in place. Search and confirmation become available after the list loads. Empty results and selectable failure details stay in the chooser, with **Retry** for a failed read. Cancel, Escape, or closing the chooser cancels the read and waits for it to finish. **Confirm branch & compare** immediately checks the latest source for commits missing from the current branch and shows the Git conflict comparison. If the current branch already includes every source commit, the result says it is up to date; **Back to Git** returns to the commit controls without a checkpoint, merge, or recovery record. If incoming commits exist, the result shows their count and any conflicts before **Review local merge…** opens the approval step. Known conflicts require manual resolution if you approve the merge. **Config → Change release branch…** also changes the saved source. The choice is stored in local Git configuration and bound to the remote URL; confirming the unchanged source does not rewrite it. Both source and destination must use the same fetch/push repository for this workflow.

**Git-only conflict test**, beside the merge button, opens the same branch verification and runs the comparison immediately after confirmation, without waiting for agents or queues. Its result opens in the Git workspace, with incoming commits, conflict paths, exact compared commits, and Git diagnostics. The result is also retained in the dashboard's **Next commit** comparison when no separate dashboard check is pending. The comparison uses the current committed branch and the latest selected remote source with `git merge-tree --write-tree`; source or local branch changes during the check discard the result and require another comparison. The check does not start a merge, stage, commit, push or change local files, HEAD, the index or cached remote refs. It downloads missing Git objects and may write temporary merge-result objects. No application build or tests run. Uncommitted edits, untracked files and changes inside submodules are excluded; the result identifies the exact commits checked and does not guarantee that an actual merge including those edits will be conflict-free. Git 2.38 or newer with modern `merge-tree` support is required for conflict simulation; **Merge Locally** skips that simulation when the current branch already includes the exact source commit. Unsupported simulation, unavailable history and command failures are reported as unavailable checks, never clean results. Checks requested from the dashboard remain manual queued checks. Background checks suppress credential prompts and require recognized credential helpers and existing verified SSH trust.

The check refuses configured external merge drivers and renormalizing external filters because those commands could change files. No actual merge or automatic conflict resolution is used as a fallback.

The preparation review identifies the current branch and explains the local checkpoint; it does not ask for a new branch name. After approval, the launcher rechecks the reviewed branch, local state, remote configuration, and exact source commit, then fetches the tracked source. A changed source or failed fetch stops before creating a checkpoint or recovery record. If incoming commits remain, the launcher preserves dirty local files in an automatically named local checkpoint commit on the current branch, then merges the exact fetched source commit with no automatic stash or merge commit. Status text reports source verification, fetching, incoming history, checkpointing, integration, and the result. This preparation requires an existing local commit and shared source history. It never creates a branch, pushes, or opens a commit-and-push review automatically.

If Git reports conflicts, a dedicated window lists the affected paths. Resolve and stage them in your editor or Git, then refresh. A conflict-free result stays local. When ready, choose **Commit all & push…** to review the destination branch and an editable prepared commit message; this same action finishes a tracked merge or publishes ordinary local changes. Closing its review leaves the work local. If you choose a new destination while a merge is pending, the launcher commits that merge on the current local branch first, then creates the new branch from the result and pushes it. Other existing local or remote branches require a separate switch and review; they are not silently reused as new destinations.

Merge recovery stores only operation identities, branches, commit IDs and a remote fingerprint in the checkout's Git metadata. Cancellation, changed identities and uncertain push outcomes retain that record and the local work for review; nothing automatically retries or rolls back. A confirmed local commit is reused on an explicit push retry. **Clear merge tracking…** only dismisses the launcher's record after you review the Git state; it does not undo a merge, delete checkpoints or prove that a push completed. Standalone **Push** remains available for existing-commit retries outside a tracked merge; a pending tracked merge must go through **Commit all & push…**. If the branch-creation reflog has expired or is unavailable, the dialog says creation history is unavailable rather than guessing from commit dates.

**Refresh local status** rereads local data. Use **Fetch** to update remote comparisons. Review canceled or interrupted operations before retrying; their outcome can be uncertain.

Dashboard startup checks saved Git connections in configured project and service folders quietly in the background. Opening **Git…** shares an unfinished check or reuses authentication verified earlier in this launcher session. Older successful checks allow the workspace to open while a silent recheck runs; the connection status says when verification came from earlier in the session. Git still checks access for each network operation. These checks do not fetch branches, stage, commit or push.

If the folder has no Git repository, or a local repository has no remote, setup begins with **Existing online repository** or **New repository**. Existing local history remains in place. **New repository** confirms local initialization only when needed, then guides creating an empty hosted repository and connecting its clone URL. **Existing online repository** connects an existing local repository, or explicitly reviews and clones into a verified empty non-Git folder. Nonempty folders are never overwritten; choose New repository for existing local files, or select an empty configured folder through Config. Failed clones leave partial files for inspection and never retry automatically. Custom checkout filters, including Git LFS, require cloning through Git directly.

Each screen asks for one step: provider, clone URL, authentication, then review. **Back** preserves entries; the connection name is under **Advanced**. Hosted repository creation opens your provider and is completed there. GitHub Enterprise domains and separate Azure DevOps organizations can use their own named connections. Folder and active-remote selectors appear only in explicit **Config** management.

**Config** reopens setup. Reconnect an existing destination or choose **Add connection…** to add another named Git remote without replacing the others. The review shows the actual local repository, provider, connection name and destination. Changing an existing destination requires confirmation. Git saves the remote URL and a non-secret provider hint in the repository's local Git configuration, so Enterprise domains retain their chosen provider when reopened. If the optional provider hint cannot be saved, the confirmed remote save remains in place and setup reports that distinction. Saving a connection does not upload files; choose the intended remote in the workspace before a later Git action. **Use local workspace** leaves setup available through Config while retaining its draft for this session.

HTTPS sign-in uses Git Credential Manager from Git for Windows. The launcher never asks you to paste a password or token; clone URLs must be credential-free HTTPS or SSH addresses. Setup supports standard HTTPS ports, GitHub/GitHub Enterprise, and Azure DevOps Services (`dev.azure.com` or `organization.visualstudio.com`); Azure DevOps Server is not supported by this flow. Azure CLI authentication alone does not establish Git access. SSH connections use the provider's `git` SSH user, your existing keys and a known, verified host key. A successful setup check verifies authentication and repository read access; permission to push is checked when you push. Automatic checks are bounded and noninteractive. **Check connection** and sign-in request fresh verification; interactive sign-in stays explicit. **Refresh local status** remains local.

Initialization is available only when the selected folder is outside an existing repository and requires confirmation. If Git reports a different Windows owner, the failure screen shows the exact repository and offers an explicit trust action. Trust adds only that path to your Windows user's global Git `safe.directory` list; trust it only if you recognize its source and trust its contents. The green branch editor owns branch creation and switching; **Branches** shows read-only comparisons and history.

Commit-message and setup drafts, plus latest-operation **Error details**, stay in memory outside launcher settings and published defaults. Setup drafts survive folder switches; closing with unsaved connection details asks before discarding them. Git credentials remain managed by your configured Git credential helper. The launcher uses its response privately and transiently to check the provider account, and never copies it into launcher settings or error output. If an expired Azure credential keeps returning, update that domain's account through Git Credential Manager. Opening or refreshing the workspace never stages, commits or pushes work.

## Run from source

The launcher source lives at the root of the standalone `FullStackDeveloperTool` repository. Run the commands below from the folder containing `FullStackLauncher.csproj`.

Double-click **launch.cmd**. It builds the launcher in Release mode and opens its window. Building requires Windows and the .NET 10 SDK or a newer compatible SDK.

You can also run:

```powershell
dotnet run --project .\FullStackLauncher.csproj
```

The launcher needs the same tools your projects normally use on `PATH`. For example, an ASP.NET Core and Angular project needs its backend's .NET SDK, plus a Node.js/npm version supported by its Angular frontend. The default single-file build includes the launcher's .NET runtime; it does not install SDKs, Node, npm, dependencies, or databases for your projects.

## Start with your own projects

A new Windows user starts with no projects, selected project, or developer-tool shortcuts. Source checkouts and published EXEs do not import the author's settings or carry personal project profiles. Choose **+ New project** and select the project root in the compact folder step. Continue to automatically select **Angular Full Stack**, **Console project**, or **Flutter / Dart app** from recognized project files. You can change the type before reviewing commands. Unrecognized or mixed project folders require a manual type choice. Returning to the same root preserves that choice; changing the root detects again. All types use the same setup and command review flow. The root `launcher.settings.json` is an empty example, not an automatically imported settings file.

For **Angular Full Stack**, first choose the project root folder that contains both the API and frontend. Continue to automatically find their working folders, then adjust either selection if needed. If a selected working folder belongs to a saved project, setup shows its owner; choose different service folders to create a new profile or select the saved project from the project list. The setup window fits the visible controls and scrolls when content exceeds the screen height. Command review starts with `dotnet run` in the API folder and `npx ng serve --port 4200` in the Angular folder, using a loopback API URL from `launchSettings.json` when available. Review the addresses and commands, then choose **Save project**. Scanning only reads project files; creating a profile does not start services or install dependencies.

For **Flutter / Dart app**, choose the existing package folder or a containing root folder and scan for `pubspec.yaml`. The selected package determines whether commands use Flutter or Dart. Multiple matching packages require an explicit folder choice. Only Flutter packages show the run target, offering **Windows desktop** (`flutter run -d windows --no-resident`) and **Web server** (`flutter run -d web-server --web-hostname 127.0.0.1 --web-port 4200`) presets, with `flutter pub get` and `flutter clean`. Dart uses `dart run` and `dart pub get`; change the command to `dart run bin/<name>.dart` when the package has a different entry point. The Flutter/Dart SDK and the selected target's tooling must already be installed and available on PATH. Native Flutter and Dart use process tracking; Flutter Web uses its configured loopback endpoint. Flutter's nonresident command can exit while its owned desktop app remains running. Scanning supports ordinary pubspec manifests; unsupported aliases, tags, or multiline flow syntax require manifest review or a manually configured service in the project editor.

After the first Local API start, database details appear automatically when the API reports them through `/health/database`. No database connection is entered during project setup. The launcher does not open database connections, create databases, or run migrations.

Native Flutter apps automatically show separate SQLite cards after an existing database file can be identified from the app's open files, app source, or the configured project file. Background discovery checks supported project-relative paths, `sqflite_common_ffi` storage, and app-specific Windows support/cache paths without scanning unrelated AppData folders. Each card shows the file name, full path, and availability; cards remain visible after the app stops. **In use · SQLite** means a recent Windows handle snapshot found the file open in a verified Flutter app process and its SQLite header was checked read-only. **Detected · SQLite** means only the existing file was verified. Neither label proves a successful app query. Unavailable or unsupported handle inspection falls back to file detection. Dynamic paths outside supported source patterns require an observable open file. Browser SQLite/IndexedDB storage is not inspected.

Native Flutter stays **Starting** while packages, build tools, or the runner are starting. **Running** requires the actual generated Windows app process and an observed visible app window. An exit from `flutter run --no-resident` does not finish the service while that verified app remains alive. Flutter Web stays **Starting** until compilation is ready and its local HTTP endpoint responds; a listening development server alone is insufficient. Recovered web runs also require a nonempty compiled JavaScript entry point. Command completion without app readiness is identified explicitly in the status details.

Run **Setup** if dependencies have not been restored or installed. **Clean** executes the saved clean command; it does not remove source files or install dependencies. Angular's default clean command clears its build cache.

Use the project editor to add more projects and any number of services. Each service has its own type, working folder and start command; clean and setup are optional. Web services also have a local URL and UI path. **Console**, **Dart**, and native **Flutter** use process tracking without a web address; **Flutter Web** and other web kinds use a loopback endpoint. Commands are trusted Windows shell commands executed in the specified working folder with your account's privileges.

## Archive and unarchive projects

Select a project and choose **Archive selected project** to move it out of the active sidebar. Open **Archived (N)**, select a project, and choose **Unarchive selected project** to return it to the active list. The launcher starts with the active list. If every project is archived, the Archived control remains available.

Archiving preserves the project's settings, stable IDs, inert legacy database references, notes, queue, and captured output. Running apps keep running and remain monitored; the active list shows a hint when archived projects have tracked processes. Open Archived to inspect or stop them. Batch actions apply to the selected project, and launcher shutdown still checks owned processes across all projects. Save or cancel inline project edits before archiving or changing the list.

## Console apps and executable arguments

Choose **+ New project** and select the project root. Recognized .NET console projects select **Console project** automatically; you can also choose it manually. Confirm the name and working folder, including a nested console folder when detected. Multiple detected console apps require an explicit folder choice. If no console project is recognized, setup uses the selected root for your custom command. Review the start command and arguments, then **Save project**. Use **Add console app** in an existing project's full settings editor to add another console service. There is no localhost, port, UI path, or Local/Prod API configuration to fill in. Optional clean/setup commands stay collapsed in the editor and appear on its card only when configured. Creating or saving the profile never starts its command.

Examples of start commands:

```text
dotnet run -- --mode quick
dotnet run -- "C:\Tools\Target.exe" --mode quick
"C:\Tools\Worker.exe" --mode quick
```

For `dotnet run`, arguments after `--` are passed to your console app. Use the argument names your app actually accepts for a target executable and its options. Quote paths containing spaces. Running a .NET project requires its SDK; directly running a published EXE uses that application's normal runtime requirements.

**Use executable…** selects and quotes a direct EXE command. It replaces the default `dotnet run` or an existing direct EXE path while keeping that EXE command's arguments. For an existing .NET command with arguments, enter the target path in the command so the app's arguments remain intact.

Use **Run**, **Restart**, and **Stop** on the app card, with selectable output in its console. Console apps show running process IDs and **Completed** after a successful command and its tracked children finish; failures show the command's nonzero exit code. These run results and logs are held in memory for the current launcher session. No HTTP listener or readiness response is required.

Use **Services → Add console app**, choose its working folder, then review the detected type and suggested command in the second dialog. The name, type, and command remain editable. A .NET console project suggests `dotnet run`; Docker Compose suggests a foreground `docker compose ... up` command, and a Dockerfile suggests image build followed by foreground run. Multiple matches show explicit launch options. Unrecognized folders keep manual type and command entry. Type labels such as **Docker**, **Python**, or a custom value appear on the service card. The folder and command appear in expanded details. Save adds the service while existing apps keep running; use **Run** when ready. Full project settings also support editing the console type label.

Changing a type refreshes only an untouched suggested command. **Change…** selects another folder and repeats detection; canceling that picker or an unsuccessful scan retains the current draft. Discovery reads bounded local project files without running commands or evaluating projects. Review generated commands against your app before saving; the [dotnet run documentation](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run) and [Docker run documentation](https://docs.docker.com/engine/containers/run/) describe the starter commands.

Generic Console apps and command-based APIs can share a working folder with another service in the same project. In shared folders, the launcher tracks only processes it started or recovered from its saved ownership records; it does not adopt externally started apps by folder. Other services still require separate folders, and overlapping service folders across different saved projects remain rejected.

Console commands started here are supervised together with their child processes, including executables outside the project folder and children that outlive the original command. Stop and launcher shutdown include those owned children. Applications delegated to an already-running external instance are outside that ownership. Console commands receive closed standard input; interactive prompts are not supported.

For Docker, use a foreground command such as `docker compose up` to keep the command represented as Running. A detached command such as `docker compose up -d` becomes Completed when the command exits successfully. Docker daemon container state is not inspected, and stopping a launcher command does not guarantee that daemon-managed containers stop.

To start it from source, double-click **launch-codex-monitor.cmd**. The script builds the launcher in Release mode and starts the monitor. The published EXE includes the monitor; no command script or companion file is needed. Open it from the dashboard's Alerts menu, or start it directly:

```powershell
.\FullStackLauncher.exe --codex-monitor
```

Select or enter a folder used by your Codex tasks in **Codex project folder**, then choose **Add project to watch**. Repeat for as many projects as you need. The dropdown combines remembered folder paths and working folders found in local Codex metadata. Watched folders are remembered locally even when no current task mentions them and can differ from the selected launcher profile. Matching considers tasks in each folder and its descendants, linked Git worktrees, and subagents related through their parent task. A chat and its subagents appear under one watched project: overlapping watches prefer the most specific folder containing the root chat, with deterministic matching for linked worktrees. Project labels include full-path tooltips; the detailed task table also exposes the actual working folder.

Watch the workspace where the Codex task was started. For example, a task started in `MyWorkWebsites` is not included in a watch limited to its `CascadeDigitalSolutionsCRM` child folder. When local metadata shows an unwatched containing workspace, the watched row explains the mismatch and offers **Watch workspace**, with the full path in its tooltip. This adds the containing workspace as a separate watch; it can include work across several child projects. Remove the narrower watch if it is no longer needed. Existing watches are never silently broadened, and previously completed history alone does not create popup activity.

The monitor checks every five seconds, reading local metadata once for all watched projects. Adding or removing a watch during a read immediately queues a fresh read for the updated list. Each project tracks completion independently: after observing running or queued work, it waits until that project's monitored work has completed and confirms that state for ten seconds before sounding. With sound enabled, reminders repeat every 60 seconds until dismissed. New activity stops that project's reminder on the next refresh. Merely opening an idle project does not start a reminder.

- **Dismiss reminder** silences the current batch and waits for new work.
- **Enable Sounds** turns automatic sounds on or off and remembers the choice across restarts. Turning it off immediately stops playback while every watched project, completion indicator, and the overlay keeps updating. The same toggle is available in the tray menu. Turning it on resumes eligible reminders on their next scheduled refresh; it does not replay old dismissed work.
- **Refresh** checks status immediately.
- **Hide to tray**, or closing the monitor window, keeps it running in the Windows system tray. Open it again from the tray or the dashboard.
- **Exit monitor** stops the monitor. Its tray menu also provides open, dismiss, Enable Sounds, and exit controls.

### Chat progress overlay

Choose **Alerts ▾ → Show chat progress** in the dashboard, or **Show chat progress** in the alerts window, to display a compact floating list above other desktop windows. The overlay has a transparent background with subtle light backing behind readable chat names, colored dots, and a single **Clear** button. Drag a chat row to move it and use the corner grip to resize it. It starts hidden; its position, size, and visibility are remembered. **Hide chat progress** in the dashboard or alerts window hides it while monitoring continues. Windows secure desktop and exclusive fullscreen applications may cover the overlay.

Each row represents a root chat and includes the progress of its observed subagents, with a project label and a rough percentage on the right. Yellow means running or queued; green means finished. Gray indicates unavailable status and red indicates failure. The list starts with work observed by the monitor rather than filling with old completed history. The alerts window's **Chat progress** tab shows the same list; **All tasks and agents** provides project labels and individual agent estimates beside their statuses.

Percentages marked **~N% est.** are low-confidence elapsed-time guesses, not measured work completion or a guaranteed finish time. A run starts with a 10-minute assumption; after at least three completed runs have been observed in that project during the current monitor session, new runs use the median of up to 20 observed durations. Each run keeps its original baseline. Time before the monitor first saw the run is unknown, waiting intervals are excluded, and long observation gaps restart timing. Running estimates stop at 95%; only an explicit completed status shows 100%, with chat rows also requiring completion confirmation. A chat uses its least advanced observed member, so new subagents can lower the estimate. Waiting, failed, missing, or unavailable members suppress the chat estimate. Hover an estimate for its basis. These estimates never trigger completion alerts and are not saved to disk.

Green rows remain through hiding, showing, and restarting the monitor. Use the overlay's **Clear** button to clear all finished rows, or **Clear** beside an individual green row in the alerts window to remove just that row. **Clear finished chats** is also available in the alerts window and dashboard's **Alerts ▾** menu. New activity in a chat replaces its green status. **Dismiss reminder** silences the sound without clearing finished chats.

No API key is needed. Keep Codex open while monitoring. This is an experimental integration with Codex's internal local status format, not a supported public status API. It reads `state_5.sqlite`, `thread_history_1.sqlite`, and `queue_1.sqlite` in read-only mode, with a bounded fallback to local lifecycle records. It does not monitor remote or cloud tasks. Missing, unreadable, unknown, failed, or interrupted state suspends completion alerts; an app crash is not inferred to mean successful completion. A Codex update that changes these internal formats may require updating the monitor.

Monitor preferences, watched-folder history, the watched-project list, and the reminder sound choice are stored separately from dashboard settings at `%LOCALAPPDATA%\FullStackLauncher\codex-monitor.settings.json`. An older saved single-folder selection migrates into the watch list. Retained completion markers store only task/turn IDs, project, and completion time; chat titles and messages are not saved. Moving or updating the EXE preserves this file. On a newly started monitor process, `--project` adds a watched folder alongside saved watches; other optional arguments choose a different Codex data directory or a diagnostics file:

```powershell
.\FullStackLauncher.exe --codex-monitor --project "D:\My projects\Workspace" --codex-home "D:\Codex data" --diagnostics-file "D:\Diagnostics\codex-monitor.json"
```

Use full paths for `--project` and `--diagnostics-file`. Without `--codex-home`, the monitor uses `CODEX_HOME` when set, otherwise the current user's `.codex` folder. Diagnostics contain counts and status only; they do not contain task IDs, titles, or messages. The same optional arguments can be passed to `launch-codex-monitor.cmd`.

Control the overlay from a shortcut or command line with `--overlay-command show`, `hide`, or `clear`. Commands are delivered to the existing monitor and keep its selected project:

```powershell
.\FullStackLauncher.exe --codex-monitor --overlay-command show
.\FullStackLauncher.exe --codex-monitor --overlay-command hide
.\FullStackLauncher.exe --codex-monitor --overlay-command clear
.\FullStackLauncher.exe --codex-monitor --exit-monitor
```

The final command gracefully exits the monitor.

## API-reported database health

The Database card shows the last verified database name, its API discovery source and current health. Expanded details contain API-reported information only. Discovery uses the running launcher-managed Local API's loopback `/health/database` response after a successful read-only query. Production APIs are never probed. Database names are validated before display; connection strings remain private. A name obtained from launch configuration is labeled separately and does not prove a live database connection.

Choose **Change DB** beside **Statistics** on the API card, or beside the database name, to review the API's configured working folder and discovered Local connection settings. The API card action remains visible when database health is unavailable or details are collapsed. The modal prefers `DefaultConnectionString` at the JSON root or under `ConnectionStrings`, then supports other standard connection keys for existing projects. It reads standard `appsettings.json`, `appsettings.Development.json`, and encrypted Local API overrides; Development values override matching base keys. If an API declares `UserSecretsId` and has no encrypted profile, the original Local .NET user-secrets can be staged for review with an explicit disclosure before saving. Connection strings stay masked until **Reveal connection string** is selected. Edit **Database name** to preserve the host, credentials, and other connection options, or edit the full string. Choose the intended connection key when the API has several.

**Save & restart** saves the reviewed Local configuration through the existing Windows-user encrypted API store and restarts only that API. Other Local overrides are preserved. Source configuration and externally owned plaintext .NET user-secrets remain unchanged; ordinary `dotnet` commands do not use this launcher override. Concurrent changes reject stale saves and retain the draft. Production and unsupported custom configuration providers or launch commands require the existing API configuration controls instead.

The database card remains visible while the API restarts. Completion requires a new launcher-managed Local run and a successful read-only `/health/database` response matching the requested database name. The title updates from that API response. A failed restart, different reported name, or missing confirmation within 90 seconds shows **Change not verified** and retains the saved configuration and draft for retry. Later successful health confirmation can clear this status. This check confirms the reported database name, not a separate server identity, and performs no migrations or direct database connections.

The launcher no longer opens direct PostgreSQL or SQL Server connections. Database exploration, saved connection management, row previews, account editing, schema comparison and migration preparation/application have been removed. Migration checks are handled elsewhere. API secrets/settings and Local/Prod launch controls remain available.

Existing saved database selections and comparison references remain inert compatibility data. Existing encrypted database connection libraries are left untouched and are no longer loaded. Use your separate database administration and migration tools when needed.

## Status and process ownership

The **Sections ▾** dropdown contains on/off switches for Projects, Tools, Services, Next commit, and Long Running Task. It stays open while you change switches; click outside or press Escape to close it. Open it with the keyboard using Space, Enter, or Down; use Tab or arrow keys to reach switches and Space to toggle them. The dropdown remains available to restore hidden sections, and **Show services** restores an empty workspace. Visibility is saved in your local launcher settings. Git and Notes & queue stay beside the dropdown; Functions, Alerts, Edit, and Refresh sit at the top right of the workspace header. Individual service cards start collapsed, showing their name, port or console type, status, API environment label, Statistics, and a destination-named launch button for web services. **Console ▾** sits beside the launch button and contains output actions and frontend **Open after build**. **Open in… ▾** sits immediately to the right of Console. Every service has a cog containing **Clean** and **Setup** when configured; API settings appear only for API services. Expand a card for details and conflict recovery. Inline and combined consoles and Reset layout have been removed.

Database information appears in a separate card titled with the last verified database name, without a duplicate DB tag on API service headers. Its discovery source stays beneath the title, and current health appears at the top right like service status. Expanded details contain API-reported information only; no direct database or comparison controls are available. Discovery still uses the running launcher-managed Local API's loopback `/health/database` response after a successful read-only query. Production APIs are never probed. Database names are validated before display; connection strings remain private.

Every service captures output independently of its card or console window. Use **Console ▾** for **Copy output**, **Clear output**, **Expand output ↗**, and **Copy Errors** when errors are retained. Copy and Clear are disabled when the retained buffer is empty. Service actions and new output never open the console automatically. If retained output contains an error, that service shows a separate **ERROR IN OUTPUT** indicator while its process status, including **RUNNING**, remains visible. **Copy Errors** copies all retained errors with up to 10 preceding console entries per error, in capture order, without opening the console. Overlapping context is copied once. A brief **Copied Error** popup confirms a successful copy. Clear its output to dismiss the indicator; warnings and stderr alone do not set it. **Expand output ↗** opens a resizable live window for that service, with severity filters and oldest-first, newest-first, or errors-first sorting. Reopening the same service focuses its existing window; switching projects leaves it attached to its original service.

The console windows use a dark background with mint accents, cyan commands, light ordinary output, mint success, amber warnings, coral errors, and lavender information. Timestamps and explicit labels distinguish the categories without relying on color. Compiler warnings and errors are classified from their content; stderr alone is not a failure. **Follow output** follows the latest line in chronological views; scrolling away pauses it so you can inspect and select earlier text. **Copy all**, Ctrl+C on selected text, and **Clear** are available in each console. Each service retains 600 entries used by its output actions and console window. Copy all includes every retained line even when filtered; Clear clears the service buffer and rejects older queued output while new capture continues. Output stays in memory and is not saved with settings. Existing API secret redaction applies before display.

Restarting or stopping an API/frontend clears its previous console output after validation and any required conflict confirmation. New lifecycle messages, startup output, and failures remain visible; queued output from the previous run cannot reappear. Console apps retain their command history until explicitly cleared. Hiding Services or closing a console popout leaves capture active. Output comes from commands started by this launcher; it cannot attach to an external process's existing terminal output. When you exit with apps left running, a background helper keeps their output pipes readable and discards the output without saving it. Retained console history is lost when the launcher closes, and reopening does not reattach output capture to those preserved runs. Restart an app through the launcher to capture its new output.

Database health uses the API's HTTP response and does not open a database connection from the launcher. Existing Codex diagnostic workspaces retain their own operation histories.

The dashboard refreshes process and local listening-port status automatically and captures command output. A started process is not necessarily ready to serve requests; the launch button stays gray until the service is running and ready, then turns green. Clicking a gray launch button shows a popup explaining why the service is unavailable and what to do next. Its label follows the destination: **Launch Swagger** for `/swagger`, **Launch Landing Page** for a frontend root, and the page name for a custom path. It opens the current local address in your default browser, including the UI path (such as `/swagger`) and any alternate port detected from managed service output. Hover over a green button to see its address, or a gray button to see its unavailable reason. **Statistics** and available **Change DB** controls use white text even while services are stopped; existing database configuration restrictions still apply. Service cards omit address rows and the ordinary stopped-process message; errors, conflicts, and startup details remain visible.

Only `http://` and `https://` loopback URLs are accepted in project settings. A listener already using an expected port is reported separately from a process started by this launcher. The launcher does not claim ownership of every `dotnet` or `node` process on the machine.

**Force stop** terminates the service's process trees. **Restart** performs that stop followed by the start command. These explicit actions can also stop an externally started service when its executable or command line can be tied to the configured working folder. When a verified external process owns exactly one listening port, the launcher can use that port for its URL.

When a service shows **Conflict**, its card offers **Resolve conflict & restart**. The confirmation lists the names and PIDs of the blocking processes and their current children. Confirming force stops those processes plus this service's matching processes, waits for the port to clear, and runs this service's start command. Unsaved work in the listed processes may be lost. Recovery checks process start times to avoid stopping a reused PID, protects the launcher and its ancestors, and requires another review if a replacement process takes the port. It never stops all Node or .NET processes by name. If Windows denies access or a supervisor respawns the listener, the service shows an error/conflict so you can stop it in its original application and retry. Ordinary Restart all and launcher shutdown do not clear unverified conflicts.

**Force stop all** also includes services whose ports are blocked even when the service itself is stopped. It stops normal service trees first, then reviews conflicting processes one service at a time with the same identity safeguards, leaving approved services stopped. Canceling a conflict review preserves that blocker and reports that attention is still needed. New service commands are disabled during the batch. A stopped service with a genuinely occupied port explicitly says the service is stopped and identifies the blocking PID; an exited listener or a released old detected port does not remain a conflict.

Closing the launcher with active apps opens a dark, mint-accented **Leave apps running?** window listing their project and service names. **Leave running & exit** keeps those apps active after the dashboard closes. **Force stop & exit** immediately stops the verified service process trees before closing; in-progress requests or work may be interrupted. A failed stop or handoff keeps the launcher open with an error. **Cancel**, Escape, or the window's close button keeps the launcher open without stopping apps. Cancel receives initial keyboard focus, and force stop is never the default action. Draft resolution and the separate Codex watcher choice still apply.

For later discovery, the launcher stores service IDs, configured folders, process IDs and start times, and console job identities under `%LOCALAPPDATA%\FullStackLauncher\service-runtime`. It rechecks live process identities and configured-folder evidence rather than treating a saved PID or occupied port as ownership. Unrelated listeners remain conflicts and are not automatically terminated. Reopening does not recover the applied API environment or credentials: rediscovered APIs remain unverified until the launcher explicitly starts them with a validated configuration.

## Saved projects and local storage

`%LOCALAPPDATA%\FullStackLauncher\launcher.settings.json` holds all project/service profiles, the selected project, developer-tool shortcuts, inert legacy database references, and workspace section visibility/split proportions. Source builds and published copies share this store by default. Add, edit, or remove projects in the dashboard; an intentionally empty list stays empty. Existing settings without layout preferences use the default layout.

When the local settings file does not exist, the launcher creates an empty project and shortcut library. It does not import source-folder, adjacent, or embedded profiles. Existing local settings remain in use, so updating the app on your own account preserves your setup; a new user's account gets a blank slate. Old portable files remain untouched and can be used only through an explicit `--settings` choice.

Project root paths are relative to the **settings file's folder** unless absolute. Service working folders are relative to their **project root** unless absolute. The folder browsers save relative paths whenever the folders are on the same drive. Moving only the EXE does not affect these paths. If you move a repository, update its project root in the editor. Existing folders are required when saving a project.

Choose another settings file explicitly when needed:

```powershell
.\FullStackLauncher.exe --settings "D:\My projects\launcher.settings.json"
```

An explicit `--settings` path uses only that file. A missing explicit file starts empty, and saving creates it. Saves replace the file atomically and retain its previous version as `launcher.settings.json.bak`. Malformed settings are preserved, with an additional timestamped recovery copy when possible; the app displays a warning and disables saving instead of overwriting them. Fix the file and restart, or launch with another `--settings` file. If another launcher copy or program changes valid settings while the launcher is open, restart to reload them before saving.

Project profiles and notes are ordinary local data, not credential stores. Commands containing recognizable literal passwords, tokens, or credential URLs are rejected before saving/starting; use encrypted API configuration or the launched application's credential provider. Console output is filtered for known API values and common credential formats before display/copy, but arbitrary applications must still avoid printing secrets. The launcher does not read database rows or export schemas.

## Build a single-file EXE

From this folder, run:

```powershell
.\publish.ps1
```

The script publishes exactly one file, `publish\single-file\FullStackLauncher.exe`, as a self-contained Windows x64 app. For Windows ARM64, use `./publish.ps1 -Runtime win-arm64`. Publishing may download runtime packs from NuGet. For a smaller EXE that requires the .NET 10 Windows Desktop Runtime on the destination, use `./publish.ps1 -FrameworkDependent`. Native runtime libraries are bundled and extracted by .NET when the EXE runs; no companion distribution files are required.

Publishing never reads or embeds source settings, local saved settings, credentials, notes, or project profiles. The old `-SettingsPath` publishing option and embedded seed hook have been removed. Every newly published build initializes an empty library for a new Windows user. Publishing does not change your existing local library.

Copy just **FullStackLauncher.exe** to your desktop or another location and open it. The dashboard and Codex watcher both run from this file and keep their local settings through subsequent EXE replacements. On another Windows account or machine, add your own projects and provide their development tools and credentials. Older EXEs already produced with personal embedded profiles are not retroactively sanitized; distribute a newly published build.

Republishing can replace an EXE in the same single-file output folder. Alternative output folders must remain inside this source folder. The script rejects folders containing other files, preserving older `portable` folders and their saved profiles. Use a new empty output folder when needed, then copy the resulting EXE elsewhere.
